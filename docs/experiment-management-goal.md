## The operator's workflow

An operator opens a host-defined path such as `/internal/experiments`, finds an experiment by name or slug, and sees what a decision would do now. The detail view shows availability, the current winner or rollout, cohort definitions, and current assignment counts. It must answer “what is being served?” separately from “how many memberships are stored?” The available actions depend on host permission, site configuration, and experiment state.

For a managed rollout called `checkout-copy`, creation stores an enabled experiment with the real control `checkout-copy_off` at 100% and treatments `checkout-copy_short` and `checkout-copy_detailed` at 0%. Its initial winner is `checkout-copy_off`. While pinned there, automatic resolution returns the app default and creates zero memberships. The operator launches it at, for example, 90% off, 5% short, and 5% detailed. New automatic assignments then use those weights. A person assigned off still sees the default and now has a real membership. Adjusting the split preserves existing memberships. The operator can pause or resume, or intentionally choose a winner. Show the effect on existing users before finalization. Choosing off as a final winner also returns the default.

Operational counts come from xp storage and work on a pre-existing database with analytics disabled. Count current memberships by cohort, including off and zero-count cohorts. A leave removes one current membership. A later join restores one. A pinned winner serving thousands of decisions can legitimately have zero memberships. Keep exposure counts, conversions, statistical lifts, automatic winner selection, and vendor dashboards outside this release. Existing server methods for destructive edits remain available to their existing callers. The page's action set above covers v1.

## Config, storage and decision contracts

Use this proposed public spelling consistently across the parser, generated examples, docs and tests. Keep the accepted product semantics if an intervening release establishes a compatible naming convention.

```json
{
  "management": { "allowCreate": false },
  "experiments": [
    { "slug": "existing-banner", "cohorts": ["control", "short"] },
    {
      "slug": "checkout-copy",
      "cohorts": ["off", "short", "detailed"],
      "rollout": "off-first"
    }
  ]
}
```

- **Seed ownership.** Missing `management` or `allowCreate` defaults to false. Existing config files keep working. An installation with no declared experiments can use an empty experiments array. Validate all settings and declarations before writing. Startup seeds missing slugs and skips existing database definitions, including a page-created slug later declared in config. Removing a declaration preserves the experiment. The management setting controls page/API creation and can change at the next initialization. A disabled setting still permits opt-in seeds and authorized operations on existing experiments. Return the effective create capability to the UI. Enforce it on the POST handler too. The page persists its changes exclusively to the host database.
- **Creation.** Apply the same off-first creation use case to page-created experiments and opt-in seeds. Normalize exactly one real `off` control and at least one distinct treatment. If an opt-in declaration supplies only treatment names, prepend off. Reject duplicate local names and empty treatments. Count off toward DynamoDB's total of 32 initial cohorts, including when inserted automatically. Reuse existing slug validation and qualification. A repeated or concurrent create cannot silently replace an existing definition. Store all cohorts, weights, the enabled flag, rollout state, and pinned winner in one atomic operation. An observer can see the complete pinned definition as soon as it exists.
- **Persistent state.** Distinguish “awaiting launch, off pinned”, “allocating”, and “winner selected”, including a final winner of off. Availability is orthogonal to these states. Derive labels from durable facts across restarts. Store an explicit managed-rollout marker and a revision suitable for atomic compare-and-set. Existing seeds, records without the marker, and programmatic legacy creates retain their uniform bucketing, decisions, and public contracts. Historical stored percentages alone never opt an experiment into the new behavior. Legacy experiments remain inspectable and support applicable lifecycle actions. Present uniform allocation accurately.
- **Transitions.** Launch an enabled, awaiting-launch experiment by atomically clearing the initial winner, writing the complete split, advancing the revision and entering allocation. Adjust the split of a running managed experiment in one transaction. Validate every cohort exactly once, finite values in range, and total of exactly 100%. Use integer basis points internally for operator-specified allocations, with up to two decimals in percent inputs. Select by half-open cumulative intervals over 10,000 units, so a zero-weight cohort is unreachable and a 100% cohort always wins. Use an injectable source of randomness for boundary tests. Preserve existing cohort IDs through changes.
- **Serving.** Pause takes precedence over winner, sticky assignment, and new assignment. Resume restores the previous phase and winner/split. A final winner overrides old memberships without changing their stored counts. For managed experiments, every public decision for their off control maps to `{ "slug": null }`, including when off was randomly assigned or finalized for a multivariate experiment. Preserve legacy flag-off and non-flag behavior. Keep raw `getGroup` results, the wire format, guest behavior, and existing server-side explicit `joinCohort` semantics. A successful explicit join while an enabled experiment has a pinned winner still creates a membership. The winner continues to govern what visitors see.
- **Concurrency.** Check the expected rollout revision in the same storage transaction or conditional write that commits a new managed automatic membership. A pause, reweight, launch or finalization between sampling and insertion must cause a fresh decision using current state. Bound contention retries, retain the existing concurrent duplicate-assignment resolution, and prevent mixed old/new cohort weights. Fence management commands with the revision seen by the operator. On stale data return a conflict with a refresh path. Repeated desired pause/resume and identical retried updates should have a documented idempotent outcome. Protect managed invariants at every public mutator that can touch those records, including direct server calls. Surface an actionable conflict for incompatible changes.
- **Storage compatibility.** Cover PostgreSQL, MySQL, SQL Server, MongoDB replica sets, DynamoDB and Sequelize 6 on all three SQL dialects. Put DynamoDB rollout metadata/revision on the parent where possible. The existing 32-cohort create already uses 98 transaction actions. Design list/detail/count reads to bound work per request, with pagination for large directories, indexed/grouped counting where applicable, and complete DynamoDB page traversal. Return counts as of the read and document provider consistency. Avoid hydrating every experiment and returning user records merely to calculate a total. Preserve existing schema data, seed reports, uniqueness claims, cascade behavior and setup generation. Deliver reviewed additive migration/provisioning paths for new and existing supported installations. The host applies them.

### What the operator can do

| Stored state                | What an identified user sees                                                                                                          | Management actions                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Awaiting launch, enabled    | Application default via pinned off. An automatic lookup creates no membership.                                                        | Inspect, launch with a full split, or pause.                                                               |
| Allocating, enabled         | An existing member keeps their cohort. A new member gets an assignment from the current weights. The off control renders the default. | Inspect, adjust the split for future joins, pause, or select a winner.                                     |
| Winner selected, enabled    | The winner overrides existing assignments. Current membership counts stay intact.                                                     | Inspect the winner and pause. Finalizing off and awaiting launch must look different.                      |
| Paused, any managed phase   | Application default. An automatic lookup creates no membership.                                                                       | Inspect the saved state or resume into that state.                                                         |
| Existing uniform experiment | The existing decision contract for that experiment applies.                                                                           | Inspect, pause/resume or finalize as applicable. Show how the existing bucketer allocates new memberships. |

A viewer gets the same explanation and counts with read access. Every mutation requires manage access. Creation additionally requires the host's configuration switch. Surface missing or stale data explicitly so a failed counts read can never appear as zero.

## Integration contract and code map

Publish a dedicated server-side management subpath. Supply a typed mount factory, a compiled UI with local assets, and an authenticated, same-origin management API. The host brings the database, existing session verification, authorization and listener. One compact host integration should serve the application under a configurable base path, including deep links and assets. Existing xp consumers can import their chosen server or frontend subpath without installing or importing a dashboard framework. Use the design synthesis to choose presentation details. A bundled React UI is a reasonable default.

An illustrative installation using the proposed API follows. Define and typecheck the final public signature in a consuming project. The host callbacks here are application code.

```ts
import { initializeXp } from "@frostme/xp/server";
import { createXpManagementHandler } from "@frostme/xp/server/management";

const runtime = await initializeXp({ connection: appDatabase });
const basePath = "/internal/experiments";

app.use(basePath, authenticateSession);
app.use(
  basePath,
  createXpManagementHandler({
    runtime,
    basePath,
    access(request) {
      if (hasPermission(request, "experiments:manage")) return "manage";
      if (hasPermission(request, "experiments:view")) return "view";
      return "deny";
    },
  }),
);
```

Separate management access from the end-user identity used for cohort decisions. Check host authorization on each read/write and honor `allowCreate` on every browser-facing create entry point. Default to denied when the host supplies no authorized operator. Keep `CohortRuntime` narrow. Extend the full server runtime or a dedicated management service with typed read models and commands. Use a neutral Node HTTP integration with a working Express example and documented Fastify/Nest mounting recipes verified where supplied. Enforce the host's base path, request limits, same-origin mutation protection for cookie-authenticated deployments, and private cache policy. Give each host instance its own runtime and config.

A minimal API under the mount can expose capabilities, a paginated experiment directory, detail with cohort counts and revision, create, launch, adjust allocation, pause, resume and finalize. Identify experiments by validated slug and cohorts by their validated identifiers. Choose a consistent conditional request mechanism for writes, such as ETag/If-Match. Return typed field errors, a missing-experiment response, a forbidden response and a stale-revision response. The UI preserves split inputs on validation or transient failure and offers a refresh/review on conflict. Test the API directly as well as through the page. Derive effective permissions and state-dependent actions on the server.
