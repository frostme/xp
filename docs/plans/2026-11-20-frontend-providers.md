# Frontend providers for xp

## Cloud agent assignment

Implement this plan in `frostme/xp`. A developer should be able to install the package in an existing Vue, Angular, Svelte, Astro, or Solid app, run `xp setup`, review its proposed wiring, and render the same authenticated experiment decision as React. Deliver the work as an ordered stack of green PRs. The maintainer owns merging and publication.

Start the first implementation branch at current `origin/main`. Read this document from `frostme/frontend-providers-plan`, which is a plan-only branch. The planning baseline is `de50197856c971b3726fb4369a27ddb20fd21966`, after the installed React journey landed. Read `AGENTS.md`, `docs/roadmap.md`, `docs/experiments.md` and `docs/cli.md`. Compare the baseline to the checkout before editing. The instructions below contain the interview decisions and can be executed from a fresh clone.

### What ships

- Five native frontend integrations in the existing `@frostme/xp` package. Solid has two builds. Existing React consumers gain the shared implementation and SSR error preload support through compatible additions.
- A public, framework-independent session/subscription API for custom frontends, the existing REST and GraphQL loaders, and a helper for server-side request-local decisions.
- Setup for the five frameworks, conventional React DOM, Nuxt, SvelteKit and SolidStart. Recognized entry points get a precise, previewed edit. Custom layouts get generated helpers, a runnable example and a manual mount instruction. Astro supports plain pages and islands using each of its compatible official React, Vue, Svelte and Solid 1.9 integrations.
- Native SSR, a packed browser journey for every setup profile, and authenticated PostgreSQL journeys covering each adapter with the three existing server transports represented. Each PR includes consumer documentation, tests and working CI.

## Public decision and hydration contract

Put framework-free implementation in `src/client/session.ts`, `src/client/preload.ts` and `src/client/gates.ts`. Export the public values and types through `@frostme/xp/client`. Keep gate parsing private. Expose the following public declarations. Existing exports from `/client` and `/react` continue to typecheck for installed consumers.

```ts
type AssignmentSnapshot =
  | { status: "loading"; slug: null; error: null }
  | { status: "ready"; slug: string | null; error: null }
  | { status: "error"; slug: null; error: Error };

type XpPreload = {
  initialAssignments: Readonly<Record<string, string | null>>;
  initialErrors: readonly string[];
};

type XpSessionOptions = Partial<XpPreload> & {
  loader?: "rest" | "graphql" | AssignmentLoader;
  experimentHost?: string;
  endpoint?: string;
};

declare function createXpSession(options?: XpSessionOptions): {
  getSnapshot(slug: string): AssignmentSnapshot;
  getServerSnapshot(slug: string): AssignmentSnapshot;
  subscribe(slug: string, notify: () => void): () => void;
  refresh(slug: string): Promise<void>;
  dispose(): void;
};

declare function createXpRequest(
  load: AssignmentLoader,
  options?: { signal?: AbortSignal },
): {
  resolve(slug: string): Promise<Exclude<AssignmentSnapshot, { status: "loading" }>>;
  preload(slugs: readonly string[]): Promise<XpPreload>;
};
```

`AssignmentLoader` is the existing callback shape `(slug, {signal}) => Promise<string | null>`. Keep its current `/react` import and also export it from `/client`. Preserve the existing `CohortLoader` call form with optional call options. Framework consumers continue to see the snapshot fields plus `refresh(): Promise<void>`. The provider accepts the common options plus a reactive `sessionKey?: string | number`. A custom headless consumer owns its session instance and disposes/replaces it when its account or transport changes.

**Lifecycle**

1. Read-only snapshot access is synchronous, returns a stable reference between changes and starts no I/O. Subscribe after client mount. Two gates and a primitive for one slug share one request. Keep settled values across consumer unmount/remount within the same session. Last unsubscribe schedules cancellation of an outstanding request after the existing microtask grace period.
2. Refresh with an active subscriber publishes pending, replaces an initial request and shares an in-flight refresh. Refresh without subscribers resolves without starting work. Reject malformed or wrong-experiment results into the error state. Aborted or superseded work cannot publish a late success or failure, even if the loader ignores its signal. Unsubscribe and dispose are idempotent. Dispose immediately aborts active work, detaches listeners and releases entries. Consumers acquire a new session for subsequent use.
3. Replace the store **before descendants see the new account** when session key, loader identity, endpoint or experiment host changes. A recreated preload prop alone has no effect. A new session starts empty even if the host passes the original preload again. Validate and retarget reactive experiment slugs when they change. Unsubscribe from the previous entry. Scope nested providers independently and reset the inherited experiment at a provider boundary.
4. A local cohort name needs an enclosing experiment. A standalone gate needs a qualified `experiment_local` name. A default needs an enclosing experiment and takes no slug. Reject invalid slugs or a conflicting qualified prefix. The nearest experiment wins. Pending shows the optional loading content. Ready with a qualified decision renders every matching gate. Ready with null and error render every default. An unmatched treatment renders no gate. Only matching gates instantiate their children. Preserve React’s treatment of ordinary children directly under an experiment boundary.

**Server request and hydration**

Instantiate `createXpRequest` once per incoming request. An authenticated host can pass `async slug => (await runtime.resolveCohort(userId, slug)).slug`, or use a loader explicitly bound to that request's trusted endpoint and credentials. The helper memoizes by slug, including in-flight work and failure, for that request only. `preload` validates input names, runs the host's explicit unique slugs concurrently and returns just those results. Repeated calls and awaited Astro components share the same memo. Treat request cancellation as cancellation. Release the request object when the response finishes.

The serialized payload contains qualified slug strings, explicit nulls and a list of failed experiment names. A successful sibling survives another slug's failure. The provider reconstructs a generic `Error("Failed to resolve cohort")` for an initial error; the host can log the original cause server-side. Validate all keys and values, reject contradictory success/error entries, and handle legal names such as `constructor` using own-key lookups. Pass the payload through native framework serialization. Keep session secrets, raw exceptions, request objects, credentials, loaders and database handles on the server.

| Server input           | HTML and first hydrated render          | Browser request                                                   |
| ---------------------- | --------------------------------------- | ----------------------------------------------------------------- |
| Qualified assignment   | Matching branch                         | Zero until explicit refresh                                       |
| Explicit null          | Default with ready status               | Zero until explicit refresh                                       |
| Sanitized error marker | Default with error status               | Zero until explicit refresh. A successful retry clears the error. |
| Slug absent            | Pending or supplied loading placeholder | One after the first mounted subscriber                            |

Serve personalized HTML/data with request-private cache behavior, including `Cache-Control: private, no-store` in the authenticated fixtures. For prerendered pages, produce a neutral pending shell or a deliberate public fallback at build time. Start visitor-specific work on an on-demand request or in a hydrated browser. The application supplies an opaque, non-secret account/session revision to the browser and rotates it on login, logout and account switches.

```ts
// In the route after the host has authenticated this request.
const decisions = createXpRequest(async (slug) => (await xp.resolveCohort(userId, slug)).slug);
const preload = await decisions.preload(["checkout-banner", "delivery-copy"]);
// Serialize preload with the route and pass its two fields to the UI provider.

// An installed, headless browser consumer. Call the returned functions on teardown.
const session = createXpSession({ ...preload, endpoint: "/api/xp" });
const readCheckout = () => session.getSnapshot("checkout-banner");
const unsubscribe = session.subscribe("checkout-banner", () => renderCheckout(readCheckout()));
renderCheckout(readCheckout());
unsubscribe();
session.dispose();
```

## Working conventions for the stack

Each provider PR owns its export, optional peers, compiler rules, CLI templates, packed tests, live case where applicable, and documentation. PR 2 introduces the registry incrementally; each newly recognized profile enters the matrix in its own PR. Use a fixture layout of `scripts/fixtures/frontend/<profile-id>/`. Place shared app scaffolding and server adapters outside the runtime package. Copy stock fixtures to temporary directories before invoking setup. Record the tested dependency versions in the lockfile or fixture manifest. Never require a local checkout of this plan or a machine-specific absolute path to run a test.

To prepare a cloud checkout, install the Node and Bun versions in `mise.toml`, then run `bun install --frozen-lockfile`. Use the same additional package managers as the code-quality workflow for generator smoke tests. Install Chromium with the repository-pinned Playwright CLI and its Linux dependencies in browser jobs. Use `bun run ci` plus the explicit transport, packed host, database and browser jobs, since the `ci` script covers only part of the workflow. If Docker or Chromium is unavailable in a cloud worker, push the draft slice and use the corresponding GitHub Actions jobs for evidence. Record the result from the job that actually exercised the feature.
